## 1. Executive Summary

Phase 2 added the integration spine: post-2.7 audit repair (2.7.5),
the headless single-game orchestrator (2.8), critical leak repair plus
tactical termination plumbing (2.8.5), and the headless tournament
harness (2.9). All 279 tests pass, `mypy --strict` reports
`Success: no issues found in 37 source files`, `ruff` and
`ruff format --check` are clean, `lint-imports` reports `1 kept,
0 broken`, and `validate_task_docs.py` / `generate_prompts.py --check`
are green (`57 tasks and 57 prompts`, `All 57 prompts are in sync`).

The leak firewall is hardened: 2.8.5 added a recursive value-scanner
to `eval/leak_test.py` that walks every packet's string values and
flags `impostor`/`crewmate`/`crew` substrings outside
`self_state.role`. The scanner self-tests pass, and an independent
walk of 605 packets from a fresh `seed=42` 200-tick orchestrator run
returns zero violations.

The principal blocker is **tactical termination**: across the
audit-prompt-prescribed seed sweep `{0, 1, 2, 7, 42, 100}` and a
100-game tournament, the rule-based agents almost never produce a
decisive `CREWMATES` or `IMPOSTORS` outcome. Six-seed sweep: 5×
`TICK_BUDGET_REACHED`, 1× `MEETING_PHASE_REACHED`, **0** decisive.
100-game tournament: `crew_wins=0`, `impostor_wins=2`,
`tick_budget_reached=75`, `meeting_phase_reached=23` — Phase 2 Merge
Criterion "Both decisive sides win > 20% of decisive games" fails
(crewmates are 0% of decisive games; the 2 IMPOSTORS wins are 100%
of just 2 decisive games). The 2.8.5 DoD bullet "confirm at least
one seed reaches `CREWMATES` or `IMPOSTORS` outcome (not all
`TICK_BUDGET_REACHED`)" is unmet on the prescribed seed range.

The principal findings are:

1. **[Critical] Six-seed sweep produces zero decisive outcomes**, in
   direct violation of Task 2.8.5 DoD (§6.3, §10.1).
2. **[Critical] Phase 2 Merge Criterion `> 20% on each decisive side`
   fails** — 100-game tournament has only 2 decisive games, both
   IMPOSTORS (§6.5, §10.2).
3. **[High] Impostor `_scored_targets` does not filter dead
   players** — once the impostor kills a crewmate, the dead player's
   stale `saw_player` event remains the highest-scoring "isolated"
   target forever, so the impostor oscillates between rooms chasing
   a corpse (§10.3).
4. **[High] Tournament harness leak self-test re-introduces the
   exact regex Task 2.8.5 forbade in `tests/`** (§6.2 / §10.4) —
   `tests/eval/test_balance_eval.py:258` contains the literal
   `"impostor-1"` id; the 2.8.5 DoD prescribed grep
   `git grep -nE "['\"](player|impostor)-[0-9]+['\"]" tests/`
   "must be empty" but is not.
5. **[Medium] Task 2.8.5 modified five files outside its declared
   `Files in scope`** (§6.7 / §10.5).

No regressions in the boundary contracts, the engine, or the prior
agent-layer Pass items. The orchestrator owns all engine imports;
`agents/` imports neither `engine/` nor `orchestrator/`.

## 2. Verdict

**Not ready for Phase 3.** The Phase 2 Merge Criteria from
`tasks/phase-2.md:957-961` cannot be claimed met until the
crewmates achieve > 20% of decisive games and at least some seeds
in the sweep terminate decisively. Phase 3 is gated on a working
tactical baseline because the meeting-state-machine (Task 3.8 /
3.12) and meeting-orchestrator integration assume the orchestrator
loop sometimes reaches `MEETING_PHASE_REACHED` with at least one
crewmate alive *for non-trivial reasons* and that the LLM layer
can compare its decisions against decisive baselines.

Recommended sequencing: a small follow-up task (call it 2.9.5) that
fixes the impostor stalemate (filter dead players from
`_scored_targets`, or add a "give up on stale sightings" timer),
re-runs the sweep, and re-runs a 100-game tournament. Phase 3
unblocks once both decisive sides clear the 20% bar.

The leak-test scope, determinism through `HeadlessGame`, the
orchestrator's clean meeting pause, and the role-neutral id rename
are otherwise sound — if the impostor termination bug is fixed,
the boundary work for Phase 3 is in place.

## 8. Specific Questions for the Orchestrator + Tournament Layer

1. **Is `MEETING_PHASE_REACHED` a single, well-named pause point that
   Phase 3.12 can replace?** — Yes.
   `orchestrator/game.py:162-167` is the only site that checks for
   `state.phase == "MEETING"`. Replacing those six lines with a call
   to a future `MeetingManager.run(state, agents, ...)` is
   surgically clean. Phase 3.12 will not need to refactor the
   surrounding loop.

2. **Does `TickScheduler` interpose cleanly on per-agent live-mode
   deadlines?** — Yes by construction.
   `orchestrator/scheduler.py` is an isolated frozen dataclass with
   one method. The orchestrator polls `should_continue(state.tick)`
   exactly once per loop iteration
   (`orchestrator/game.py:143-148`); a future scheduler can layer
   per-agent deadlines without touching the loop body.

3. **Is the impostor's tactical loop testable via the same
   harness?** — Yes for unit tests, no for integration.
   24 unit tests in `tests/agents/test_impostor_policy.py` pin the
   FSM transitions in isolation. The integration loop, however,
   does not have a test that pins terminal behaviour for the
   impostor (e.g. "when the impostor's only sighted target is dead,
   the impostor must not loop indefinitely"). This is the exact gap
   that produces §10.3.

4. **Does the tournament harness preserve per-game determinism?** —
   Yes. Each `HeadlessGame` builds its own `EngineRng` from
   `seed_initial_state(seed=...)`, and the per-game replay path is
   `replay-seed-{seed}.jsonl`. Re-running the same seed via
   `run_balance_eval` produces byte-identical replays
   (the per-`HeadlessGame` byte-identity test transitively
   guarantees this).

### 10.3 [High] `ImpostorPolicy._scored_targets` does not filter dead players, producing a stalemate loop

- **Status:** Fail (integration-level bug).
- **Evidence:** Trace of seed 0 at HEAD:

  - p-3 is the impostor; p-4 is a crewmate killed at tick 4 in
    REACTOR.
  - p-3's last 30 actions (ticks 970–999) oscillate
    `move ENGINEERING ↔ REACTOR ↔ ENGINEERING ↔ ...`.
  - `agents/tactical/impostor_policy.py:219-265`
    (`_scored_targets`) walks every `saw_player` event in memory and
    keeps the latest sighting per player. It does NOT filter
    sightings whose subject is now dead (the impostor has no
    `saw_body` event tying p-4's body to p-4's id, because
    `BodyState.player_id` is hidden by the firewall).
  - With p-4's stale sighting in REACTOR (`co_present=0` at sighting
    time), p-4 scores higher than the alive crewmates camped in
    CAFETERIA (each with `co_present>=1` when seen), so the impostor
    keeps moving toward REACTOR forever.
- **Why it matters:** This is the root cause of §10.1 and §10.2.
  Not a code-correctness issue (no assertion fires, no test fails),
  but a tactical-FSM completeness issue: the impostor's IDLE branch
  cannot recognise "all my sighted targets are unreachable / dead"
  and degrade to wait or random walk.
- **Recommended action:** Two minimum-viable fixes are available:
  (a) Filter `_scored_targets` to drop sightings whose latest tick
  is older than some staleness window (e.g. > kill_cooldown ticks
  ago); or (b) Cross-reference each candidate against the latest
  `global_status.alive_players` count to detect "fewer alive
  players than I have sightings of" and prune. Either is small;
  both should ship with a regression test that pins "with all
  sightings stale or dead, the impostor wait()s within N ticks".

**Direct answer: not ready.** The Phase 2 Merge Criteria are unmet
on the live tournament, and the underlying impostor-stalemate plus

can fairly evaluate LLM-driven meeting / strategic-reasoner

Answers to the §7 questions:

1. **Determinism boundary debuggability.** Strong-but-not-watertight.
   `orchestrator/replay.py` records per-tick `state_hash`, and
   `test_headless_game_replay_is_byte_identical_for_same_seed`

   benefit from extending this test to a longer horizon (§10.6) so
   that an LLM-introduced non-determinism that manifests only after
   the meeting-state-machine fires has a clear isolation seam. The
   replay format does NOT capture engine events — only actions and
   `state_hash` — so a regression that produces the same final
   state from different intermediate events would slip through.
   Recommendation: extend `ReplayEntry` to optionally include the
   per-tick event list (or a hash of it) before Phase 3 begins.

2. **`agents/memory/` shape vs. Phase 3.3 requirements.** Sufficient.
   Task 3.3 (`tasks/phase-3.md:96-131`) introduces `agents/memory/store.py`

   `WorkingMemory` (`agents/memory/working.py`), and `BeliefState`
   (`agents/memory/beliefs.py`). Each existing module exposes
   read paths sufficient for `render_for_prompt`'s "role + tasks
   completed + recent observations + beliefs + open contradictions"
   sections per DESIGN.md §6.6. No shape gap.

3. **Orchestrator pause point for Phase 3.8 / 3.12.** Clean.
   `orchestrator/game.py:162-167` is the single, well-named site
   that returns `MEETING_PHASE_REACHED`. Phase 3.12 can replace
   those six lines with a `meeting_manager.run(state, agents,
   public_map, ...)` call and continue the loop. The surrounding
   `while state.phase == "PLAY"` guard does not need to change.

4. **Leak scanner reach for Phase 3 LLM consumption.** Sufficient
   at the packet boundary, insufficient at the prompt boundary.
   `_assert_no_role_bearing_values` walks every emitted packet, so
   anything `agents/perception.ingest_packet` writes to memory
   inherits the firewall. But the Phase 3.3 `render_for_prompt`
   output — the actual string handed to the LLM — is not yet
   subject to the same scanner. A regression that, say,
   accidentally serialises a `BeliefState`'s `_alibi_claims` payload
   verbatim with a role-bearing field would not be caught. Phase
   3.3's DoD should add a leak-scanner pass over rendered output.

5. **Phase-3 prerequisites from this audit.** Yes:
   - **§10.1 / §10.2 / §10.3** — fix the impostor stalemate so the
     tournament produces decisive outcomes; the LLM strategic
     reasoner needs a working baseline to compare against.
   - **§10.7** — decide and document the Phase 2 Merge Criterion
     interpretation (rule change vs. criterion rewording); Phase 3
     work that targets the criterion needs a stable definition.
   - **§10.6** — extend the byte-identity test horizon before LLM
     non-determinism is introduced.
   - **§10.4 / §10.5** — clean up the scope/grep wording so Phase 3
     contributors and audits have a consistent rule to apply.

   Items §10.6 / §10.7 are small but should ship in the same
   pre-Phase-3 follow-up PR as the §10.3 fix; §10.4 / §10.5 are
   pure documentation and can be folded into the same PR.
