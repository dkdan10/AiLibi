## 8. Specific Questions for the Phase 4 Layer

1. **Is the replay format ready for the eval harness?** **Yes.** [orchestrator/replay.py:86 MeetingReplayEntry](orchestrator/replay.py#L86) carries the full transcript (reports + statements in canonical order), ballots, contradictions, per-call `LLMCallRecord` telemetry, `prompt_versions`, plus `state_hash_before` + `state_hash_after`. A spectator UI can render meeting transcripts from the `transcript` field directly; a Phase 5 metrics eval can compute per-meeting vote tallies from `ballots`, contradiction counts from `len(contradictions)`, and per-call cost from `sum(call.cost_usd for call in entry.llm_calls)`. Per-game cost is `sum(call.cost_usd for entry in read_meeting_entries(path) for call in entry.llm_calls)` — straightforward, but no helper exists (see C-4 below).

2. **Does the meeting interpose point allow Phase 4's WebSocket broadcasts?** **Yes, with one nuance to plan around.** The `MeetingRunner.run_meeting()` Protocol at [orchestrator/game.py:124](orchestrator/game.py#L124) is one opaque async block — it returns a `MeetingArtifacts` bundle after the whole meeting has resolved. Intermediate states (report submitted, round started, vote cast) are NOT directly observable from the orchestrator's loop. For Phase 4.2 game broadcast, the natural integration point is to wire the broadcast layer INSIDE the `MeetingRunner` implementation (alongside the `_RecordingLLMClient`-style wrapper, e.g. a `_BroadcastingMeetingManager` decorator) rather than at the orchestrator/runner boundary. The clean way: a Phase 4 implementation provides a custom `MeetingRunner` that wraps `MeetingManager` similarly to how `DefaultMeetingRunner` does, and emits intermediate WebSocket events at the same points the recording wrapper captures LLM calls. The substrate supports this — no Phase 3 refactor needed.

3. **Are there any Anthropic-specific assumptions in `agents/strategic/reasoner.py` or `meetings/manager.py` that would block a future provider swap?** **No.** `grep -nE "anthropic\|cache_control\|extended_thinking" agents/strategic/ meetings/ orchestrator/ llm/budgeted_client.py` returns empty. `BudgetedLLMClient` uses provider-neutral USD-per-token rates (defaults at [llm/budgeted_client.py:69-70](llm/budgeted_client.py#L69) — `6e-6` input, `30e-6` output — "calibrated to be roughly twice typical premium-tier pricing so a tight budget tripped in pre-flight is a true ceiling"). The four `.j2` templates do not name a specific model. `call_kind="meeting"` / `"trigger"` is the provider-neutral tier selector.

4. **Does the cost-tracking machinery support the ≤ $0.30/game merge criterion check?** **Partially.** The per-call cost is on `LLMCallRecord.cost_usd`; per-meeting cost is computable as `sum(call.cost_usd for call in entry.llm_calls)`; per-game cost is computable as `sum(...)` over all meeting entries. **What's missing**: (a) no production code constructs a `BudgetedLLMClient` so the budget cap is not enforced during the run (H-1); (b) no helper function aggregates per-game cost from a replay file. The eval will need to write its own reduction (trivial — 3 lines) AND wire the budget adapter so the cap is enforced at call time, not just measured post-hoc.

5. **Did Phase 3 introduce any new Phase 2 risks?** **No.** 100-game tournament byte-identical to post-3.8 (58/35/0/7); six-seed sweep byte-identical (11/9/7/7/8/10); 500-tick same-seed byte identity PASS; leak scanner walks 6,550 packets with zero violations. The orchestrator diff preserves the `meeting_runner=None` path verbatim — the addition is an `if meeting_runner is None: return MEETING_PHASE_REACHED else: dispatch` branch at [orchestrator/game.py:646](orchestrator/game.py#L646), so Phase 2 callers that never construct a runner see identical behaviour.

6. **New Critical/High findings introduced by this audit window?** **One High (H-1)**: `BudgetedLLMClient` + `GameBudget` are not wired into the orchestrator's meeting flow. This must be addressed before the real-provider 50-game eval (Stage 3) can safely run. It does NOT block Phase 4 dispatch.

7. **Is the substrate ready for Phase 4 dispatch after the real-provider eval passes?** **Yes.** Phase 4's first task (4.1 FastAPI scaffolding) is a fresh module that consumes the existing orchestrator + replay surface; no Phase 3 work is missing for it. Phase 4.2 (game broadcast) needs a `MeetingRunner` wrapper that emits intermediate events (see question 2) — the substrate supports it natively. Phase 4.3+ (React frontend) consumes WebSocket events the broadcast layer emits. The replay format (R-9 closure) carries every artifact a spectator UI needs.

## 10. Defects and Risks

### H-1 [High] `BudgetedLLMClient` + `GameBudget` not wired into the orchestrator's meeting flow

- **Status:** Open. C-5 from post-3.8 carried into the close of Phase 3.
- **Evidence:** `grep -rn "GameBudget\|BudgetedLLMClient" orchestrator/ meetings/` returns empty. `DefaultMeetingRunner.__init__` at [orchestrator/game.py:240](orchestrator/game.py#L240) accepts an `llm_client: LLMClient`, wraps it in a `_RecordingLLMClient`, and passes that into `MeetingManager(llm_client=…)`. There is no `GameBudget` construction in the orchestrator and no `BudgetedLLMClient` interposition. `scripts/run_game.py` and `scripts/run_tournament.py` don't construct a meeting runner at all, so the question is moot for the headless CI path; but any consumer that wires up a `DefaultMeetingRunner` (including the real-provider 50-game eval) will be using a raw `LLMClient` with no per-game budget enforcement.
- **Why it matters:** The Phase 3 Merge Criteria require "Cost per game ≤ $0.30 or provider equivalent." That criterion cannot be enforced at call time from current code — it can only be measured post-hoc from the replay log. A single runaway meeting that issues a long prompt to a 4M-token-context model could blow the budget without any fail-loud signal. The strategic-reasoner tests demonstrate the adapter slots in transparently ([tests/agents/test_strategic_reasoner.py:861](tests/agents/test_strategic_reasoner.py#L861)); the gap is purely a wire-up at the orchestrator layer.
- **Recommended action:** Add an `optional budget: GameBudget | None = None` kwarg to `DefaultMeetingRunner.__init__`. When `budget is not None`, wrap the `llm_client` in `BudgetedLLMClient(inner=llm_client, budget=budget)` before passing it through the `_RecordingLLMClient`. Add one regression test that constructs a `DefaultMeetingRunner` with a tight-cap budget, runs a meeting that would exceed the cap, and asserts `BudgetExceededError` propagates from `run_meeting()`. This is ~30 LOC + 1 test. **The fix should land before the real-provider eval runs.**

### M-1 [Medium] Tournament harness (`eval/balance_eval.py`) cannot drive a `MeetingRunner`

- **Status:** Open. Scope discipline observation, not a regression.
- **Evidence:** `grep -n "meeting_runner\|MeetingRunner" eval/balance_eval.py scripts/run_tournament.py scripts/run_game.py` returns empty. `eval/balance_eval.py::run_balance_eval` constructs `HeadlessGame(...)` without a `meeting_runner=` kwarg, so the 7/100 `meeting_phase_reached` outcomes in the current tournament report are the Phase 2 early-exit branch — the LLM-driven meeting flow never runs in the headless tournament. The 100-game tournament numbers are therefore identical to post-3.8 by construction.
- **Why it matters:** The Phase 3 Merge Criteria require "50-game eval: full-LLM games complete end-to-end using fake-provider tests in CI." The CI test surface that satisfies this is `tests/orchestrator/test_replay_meetings.py::test_byte_identical_long_horizon_meeting_replay` (one game with one meeting). There is no harness that drives 50 (or 100) games with the meeting flow wired up. The real-provider 50-game eval (Stage 3) will need either (a) a CLI flag on `scripts/run_tournament.py` to construct + inject a `MeetingRunner`, or (b) a new `scripts/run_llm_tournament.py`. The substrate supports it (the `HeadlessGame` constructor accepts a runner); it's a wiring task.
- **Recommended action:** Defer to the real-provider eval's owner. They will need this surface anyway; folding it in as part of the eval scaffolding is the natural sequencing.

### C-1 [Concern] No production end-to-end test uses `llm.fake_provider.FakeProvider` through `HeadlessGame`

- **Status:** Open. Coverage gap, not a defect.
- **Evidence:** Orchestrator integration tests use inline custom stubs (`_ScriptedLLMClient`, `_DeterministicLLMClient`) rather than the canonical `FakeProvider`. The canonical FakeProvider is exercised at three levels (meeting manager unit, reasoner unit, per-template smoke) but never through the full `HeadlessGame` + `DefaultMeetingRunner` + `MeetingManager` path.
- **Why it matters:** The custom stubs satisfy the same `LLMClient` Protocol that `FakeProvider` satisfies, so the merge criterion is met in spirit. But a regression in `FakeProvider` that breaks its production-shape responses (e.g. introduces a non-deterministic field) would not be caught by any end-to-end test. The risk is bounded — `FakeProvider`'s response builder is deterministic by construction — but the coverage gap exists.
- **Recommended action:** None blocking. Phase 4.2 (game broadcast) will likely add an end-to-end FakeProvider test as part of its scaffolding.

### C-2 [Concern] `StrategicReasoner` is defined but unused in production paths

- **Status:** Open. Architectural surface observation.
- **Evidence:** `grep -rn "StrategicReasoner" orchestrator/ meetings/ agents/ scripts/` (excluding the file that defines it) returns hits only in `agents/strategic/prompts/__init__.py` docstring and `agents/strategic/prompts/loader.py` docstring — both documentation references, not call sites. `DefaultMeetingRunner` constructs `MeetingManager` directly with prompt callables, bypassing the reasoner. The reasoner's identity-field override, scanner-protection (`_scan_prompt_inputs`), and trigger validation logic are only exercised by `tests/agents/test_strategic_reasoner.py`. `MeetingManager` has parallel identity-override logic on its own (e.g. `_collect_statement` model_copy at the manager's line 594-601), so the production path is correct — but the reasoner's leak-scanner protection is NOT applied to prompts that go through `DefaultMeetingRunner`.
- **Why it matters:** The reasoner is a Phase 3 deliverable (Task 3.9 primary). It's well-tested but its safety properties (R-10 scanner gate on prompt inputs) only protect callers that go through it. In practice the meeting-prompt callables in `DefaultMeetingRunner` consume the same rendered memory and same templates, so a leak in rendered memory would still be caught by `eval/leak_test.py` against the audit log packets — but the scanner gate the reasoner adds (against prompt-time inputs, including auxiliary text like `meeting_trigger`) does not protect the meeting flow.
- **Recommended action:** A future hygiene task could either (a) consolidate the meeting flow through the reasoner, or (b) lift `_scan_prompt_inputs` into a shared helper that `DefaultMeetingRunner` also invokes. Neither is a Phase 4 blocker.

### C-3 [Concern] `MEETING_PHASE_REACHED` literal preserved as backward-compat

- **Status:** Open by design. Backward-compat carve-out.
- **Evidence:** [orchestrator/game.py:80 Outcome](orchestrator/game.py#L80) still includes `"MEETING_PHASE_REACHED"`, and [orchestrator/game.py:645-651](orchestrator/game.py#L645) returns that outcome when `self._meeting_runner is None`. This is by design — `scripts/run_game.py`, `scripts/run_tournament.py`, and the Phase 2 tests don't construct a runner.
- **Why it matters:** The 100-game tournament reports `meeting_phase_reached: 7` because 7 games trip the early-exit branch. A reader unfamiliar with the orchestrator might assume the LLM-driven meeting failed; in reality it never ran. Documentation/observability concern, not a defect.
- **Recommended action:** None blocking. The docstring at [orchestrator/game.py:537-545](orchestrator/game.py#L537) is clear about the semantics. A future README update could clarify the tournament harness's relationship to the meeting flow.

### C-4 [Concern] No helper for per-game cost aggregation from a replay log

- **Status:** Open. Forward-looking for real-provider eval.
- **Evidence:** `orchestrator/replay.py` exposes `read_all_entries`, `read_meeting_entries`, `read_replay_entries`. Per-game cost is `sum(call.cost_usd for entry in read_meeting_entries(path) for call in entry.llm_calls)` — three lines, but no helper packages it.
- **Why it matters:** The real-provider 50-game eval will need to compute per-game cost across 50 replays and check the `≤ $0.30` band. Writing the reduction is trivial, but every consumer doing it inline risks drift (e.g. someone forgets that `read_meeting_entries` returns only meetings, not all entries — though the naming is clear).
- **Recommended action:** Defer to the real-provider eval owner. They can add `compute_cost_usd(path)` to `eval/` (~5 LOC) as part of the eval scaffolding.
