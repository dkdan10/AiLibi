The strategy actually exercises the engine's reject path: in `_initial_state`, `p-3` is the impostor with `cooldown=0` and all three players co-located in CAFETERIA, so the first drawn `kill` succeeds; subsequent kill attempts hit `ActionRejectedError("kill is on cooldown")` and become `ActionRejectedEvent`s. The test asserts `len(lines) == 2` AND `first_entry["agent_id"] == "p-1"` AND `second_entry["agent_id"] == "p-2"` — any truncation breaks the count; any out-of-order write breaks the second assertion. **Pass.**

- **R-5 "kill drops the last task → crew wins this tick" edge case.** No unit pin (see F-2). ### F-1 [Medium] `DESIGN.md` §3.5 names `tasks_per_crewmate` as a `seed_initial_state` parameter that does not exist

- **Status:** Open.
- **Evidence:** `DESIGN.md` §3.5 "Phase 2 tournament balance — tuning levers and search order" paragraph says: *"(2) `tasks_per_crewmate ∈ {2, 3}` (a parameter on `orchestrator.seeder.seed_initial_state`) paired with `kill_cooldown_ticks ∈ {6, 4}`"* and *"Current canonical default: `kill_cooldown_ticks=4`, `tasks_per_crewmate=1`"*. Path A step 1 (`kill_cooldown_ticks=4` only) succeeded, so the seeder was correctly not parameterized — but the DESIGN paragraph reads as if it had been.
- **Why it matters:** The Phase 2 audit prompt §6.4 calls this out specifically. A future maintainer scanning the lever paragraph will look for a parameter that does not exist, or worse, assume the "current default `tasks_per_crewmate=1`" is configurable today.

Either fits in a single small edit.

### F-2 [Low] DESIGN.md §3.5 same-tick crew-win consequence is documented but unpinned

- **Status:** Open.
- **Evidence:** `DESIGN.md` §3.5 paragraph 2: *"an impostor kill which removes the last incomplete task from `state.tasks` triggers the crew win condition on that same tick. - **Why it matters:** Latent failure mode.
