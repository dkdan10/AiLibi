## 10. Defects and Risks

### L-1 [Low] Budget's `_COST_USD_CAP_SLACK` is internal; no test pins its size

- **Status:** Open. Coverage gap; behavior is currently correct.
- **Evidence:** [llm/budget.py:42](llm/budget.py#L42) sets `_COST_USD_CAP_SLACK: Final[float] = 1e-6`. [tests/llm/test_budget.py:246 test_three_dimes_does_not_false_trip_thirty_cent_cap](tests/llm/test_budget.py#L246) confirms `0.10 + 0.10 + 0.10` does not trip a `$0.30` cap (good — pins the slack is enough). `:260 test_meaningful_overrun_still_raises` confirms `$0.31` against a `$0.30` cap does raise (good — pins the slack is small enough). But no test pins the *boundary*: e.g. `cap=0.30, charge=0.30 + 1e-3` should raise, and `cap=0.30, charge=0.30 + 1e-9` should not. A future widening of the slack constant to e.g. `1e-3` would pass every existing budget test but silently allow ~$0.001 of overspend per call.
- **Why it matters:** The budget's fail-loud contract is the only thing standing between an LLM-driven sub-phase B call and an unbounded run. A silent slack-widening would be hard to detect in production; in CI it's a one-line fix to pin.
- **Recommended action:** Add ~10 lines to [tests/llm/test_budget.py::TestFloatSafeCapComparison](tests/llm/test_budget.py#L245) asserting `cap=0.30, charge=0.30 + 1e-3` raises and `cap=0.30, charge=0.30 + 1e-9` does not. Not a sub-phase B blocker.

### L-2 [Low] `render_for_prompt` last-seen suffix on a confirmed-dead player is unpinned

- **Status:** Open. Coverage gap; behavior is currently correct.
- **Evidence:** [agents/memory/store.py:338-372](agents/memory/store.py#L338-L372) appends a `(last seen in ROOM at tick N)` suffix to every belief line. The render walks `beliefs.known_players()` and pulls `working.last_seen(player_id)` regardless of whether that player has been observed dead. The intended Phase 3 use case is to surface "last seen pre-death" context — but no test asserts the suffix renders for a player whose `victim_id` appears in a `saw_body` event. [TestR6CompositeMemoryReadsAllThreeStores::test_render_uses_working_memory_for_last_seen_enrichment](tests/agents/test_memory_rendering.py#L467) uses a live (suspicion=0.7) player; if `last_seen` were silently skipped for confirmed-dead players, that test would still pass.
- **Why it matters:** Sub-phase B will lean on the renderer to give strategic agents recall about who was where right before a body was found. If `last_seen` is suppressed for dead players (it isn't today, but a future refactor could add that as an "optimization"), the prompts would lose a key piece of context.
- **Recommended action:** Add one test (~15 lines) that records a `last_seen` + a `saw_body` event for the same player, and asserts the suffix is still in the rendered output. Not a sub-phase B blocker.

### C-1 [Concern] R-10 leak-scanner reuse "or successors" hedge still applies at Task 3.9

- **Status:** Open; scheduled for sub-phase B Task 3.9 review. Task 3.3 closed the hedge for `render_for_prompt`; Task 3.9 must close it for strategic-prompt inputs.
- **Evidence:** `tasks/phase-3.md:471` still reads *"`_assert_no_recursive_hidden_fields` and `_assert_no_role_bearing_values`, or their canonical Phase 3 successors"* for the strategic-reasoner gate. The Phase 3.3 implementation reuses the helpers *directly* (good precedent set), but the textual hedge in `phase-3.md:471` remains.

- **Recommended action:** None in the current window. Sub-phase B reviewer for Task 3.9: enforce the same direct-import discipline that 3.3 established.

### C-2 [Concern] `render_for_prompt` may exceed `token_budget` when beliefs + contradictions are very large

- **Status:** Open; documented design choice, not a defect.
- **Evidence:** [agents/memory/store.py:101-106](agents/memory/store.py#L101-L106) — "the role line, tasks-completed line, beliefs, and contradictions are always retained because they are agent-essential context that the LLM cannot work around". [`_assemble_view`](agents/memory/store.py#L394) returns `non_elastic_text` (which includes beliefs + contradictions) when `remaining < header_cost`, even if `non_elastic_cost > token_budget`. [tests/agents/test_memory_rendering.py::TestTokenBudgetIsHardCap](tests/agents/test_memory_rendering.py#L729) exercises moderate budgets with no contradictions, so the boundary where beliefs alone overflow is not tested.
- **Why it matters:** The DESIGN.md §6.6 contract is "token budget is enforced — events past the budget are dropped by salience". The implementation reads "drop *observation* events"; the doc says "events" in a context that could be read either way. Sub-phase B prompts that target Sonnet-4.6 with realistic token caps (say 8k–16k for the meeting view) will rarely hit this — but a degraded path where the orchestrator passes `token_budget=200` to surface only the most-essential info would still see beliefs + contradictions pushed through.
- **Recommended action:** None in the current window. Sub-phase B reviewer: when prompt templates land in 3.4–3.7, decide whether the contract should be strengthened. Two options: (a) document the carve-out in DESIGN.md §6.6 verbatim; (b) make beliefs + contradictions elastic too (drop lowest-suspicion belief lines first under tight budgets).

### C-3 [Concern] `MeetingTranscript` shape unverified against §5.2 round-resolution semantics that Task 3.8 will need

- **Status:** Open; sub-phase B will resolve.
- **Evidence:** [meetings/schemas.py:217-225](meetings/schemas.py#L217-L225) defines `MeetingTranscript` as `tuple[ReportDocument, ...]` + `tuple[Statement, ...]`. DESIGN.md §5.2 describes the accusation rounds as a fixed sequence: "Round 1: each living agent gives an opening statement. Round 2: agents may respond to claims in round 1. (Configurable; default = 2 rounds.)". `Statement` carries `round_index`, so a transcript can be reconstructed by sorting on `(round_index, statement_id)`. But the schemas do not guarantee statement ordering, do not pin a max-rounds invariant, and have no test exercising a multi-round transcript end-to-end. Task 3.8 will need to invent the wire-up.
- **Why it matters:** A schema that allows ambiguous round ordering means each prompt template will have to enforce its own canonical sort, risking drift between templates.
- **Recommended action:** None in the current window. Sub-phase B reviewer for Task 3.8: confirm `MeetingManager` either (a) emits Statements in a canonical order and documents that, or (b) the schemas add a `round_max` invariant and the consumer enforces sort discipline.
