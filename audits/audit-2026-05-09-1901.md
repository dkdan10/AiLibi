The codebase faithfully implements DESIGN.md §0–§4 + §A through Task 2.1. The
deterministic engine is a pure function of state and action input, the
observation firewall is enforced architecturally and lint-checked, replays are

The principal findings are minor:

1. `tests/fixtures/scripted_game_vent_and_emergency.json` contains a duplicate
   actor on tick 2; eval-layer tests bypass the orchestrator boundary, so the
   engine silently accepts the duplicate. The fixture currently behaves
   correctly only because a meeting-trigger interrupts the tick before the
   second action runs (Medium).
2. `PublicMapView` adds a `vent_rooms` field beyond the Task 2.1 contract list.
   Defensible (agents need it for vent pathing), but worth flagging because the
   contract uses the word "only" (Low).
3. `api/main.py`, `tests/api/test_main.py`, and `docker-compose.yml` were not
   listed in any Phase 0 task contract, yet they exist and are tested. They
   support the §9 Phase 0 deliverable "`docker-compose up` boots an empty
   FastAPI"; the artefacts are coherent with DESIGN but were not written under
   any task scope (Low).
4. `EngineRng` serializes RNG state with `pickle` (Python-version-coupled).
   Replays are local-only artifacts per the comment, but the project should
   call this out as a portability constraint before Phase 4 ships replays to
   the spectator UI (Low).
5. ObservationPacket field shape is split between DESIGN.md §4.2 (which
   specifies `cooldown: int | None`) and DESIGN.md §A "Key Schemas (sketch)"
   (which omits it). The implementation matches §4.2; §A is labelled "sketch"
   so I treat this as documentation drift, not a binding conflict (Low).

No Critical or High findings. The boundary contracts shipped in Task 2.1 are
stable enough to support Task 2.2 without further hardening.

## 6. Architectural Invariant Audit

### I-1 Tick-based deterministic engine — Pass
- `advance_tick(state, actions, *, game_map)` is keyword-required for
  `game_map`, takes only frozen inputs (`engine/tick.py:401-471`), and returns
  `(WorldState, list[EngineEvent])` without touching any module-level state.
- No use of `time.time`, `datetime.now`, `os.urandom`, or unseeded `random` in
  `engine/`. RNG flows exclusively through `EngineRng.from_state(state.rng_state)`
  (`engine/tick.py:460-464`).
- Property test `test_advance_tick_is_total_under_arbitrary_safe_actions`
  (`tests/engine/test_tick_properties.py:95-126`) repeatedly hammers the tick
  loop with random move/wait sequences and asserts `phase ∈ {PLAY, MEETING,
  GAME_OVER}` and structural well-formedness.

### I-2 `advance_tick` is pure — Pass
- All inputs are frozen dataclasses or sequences thereof; outputs are new
  values via `dataclasses.replace`.
- The meeting-interrupt path exits before passive effects, win checks, RNG
  advance, or tick increment — verified by
  `test_meeting_trigger_interrupts_tick_before_passive_effects_and_win_checks`
  (`tests/engine/test_tick.py:747-789`) which asserts `next_state.tick ==
  state.tick`, `next_state.rng_state == state.rng_state`, and the sabotage
  timer is untouched.
- Concern note: `WorldState` exposes `Mapping`-typed fields, so callers can
  read sub-mappings; in-place mutation is rejected by `MappingProxyType`
  (`tests/engine/test_world_state.py:85-109`).

### I-3 Replays are byte-identical from seed/action log — Pass
- Independent runs of each fixture compared at file-bytes level
  (`eval/determinism_test.py:107-122`).
- I additionally ran two fresh runs of an empty 20-tick game with seed=11
  through `_state_hash` and compared per-tick hash sequences — identical for
  every tick. This satisfies the spec wording "compares full state hashes
  across two independent runs, not just final-state equality" because the
  determinism test compares the entire JSONL, every line of which contains a
  per-tick `state_hash`.

### I-4 Engine state remains engine-owned — Pass
- All `WorldState` mutations happen inside `engine/`. Orchestrator and
  observation only *read* from `WorldState`.
- AST scan: `engine/` modules import only from each other; no engine module
  imports from `agents`, `observation`, `orchestrator`, `llm`, or `api`.

### I-5 `agents/` does not import `engine/` — Pass
- `import-linter` `agents → engine` forbidden contract: KEPT.
- Both the direct-leak and the transitive-leak firewall tests in
  `tests/test_firewall.py` succeed.
- AST scan of `agents/` produced zero matches for any `engine` import.

### I-6 Agents receive only `ObservationPacket` and `PublicMapView` — Pass

  (verified by `test_agent_visible_observation_schemas_have_no_engine_imports`,

### I-7 Agents return only `ActionIntent`, never engine `Action` — Pass

### I-8 Observation firewall strips hidden information — Pass

## 7. Test Quality and Coverage Gaps

Strengths:

- The leak test is genuinely defensive: it walks the JSON-dumped packet
  recursively, reasons about action visibility against engine event witness
  lists, and even includes a self-test
  (`test_recursive_hidden_field_scanner_reports_nested_path`) that confirms
  the scanner trips on nested forbidden paths.
- The determinism test runs each fixture twice and compares the entire
  serialized replay log, so any per-tick hash divergence would surface as a
  byte-level diff.
- The property test for `advance_tick` is small (50 examples) but adequate
  for Phase 1; it proves totality on the `move`/`wait` subset that Phase 2
  agents will mostly emit.
- Mutation tests around `WorldState` mappings catch in-place edits via
  `MappingProxyType` (`tests/engine/test_world_state.py:85-109`).
- The firewall tests cover both direct (`agents/_firewall_bad_import.py`) and
  transitive (`agents/ → observation/ → engine/`) leaks.

Gaps:

- The property test's action vocabulary is intentionally narrow (move + wait).
  Kill/vent/sabotage paths are tested unit-by-unit but not under random
  interleavings; this is acceptable per the test's docstring but should be
  re-examined before Phase 3 LLM ablation work, where richer property
  coverage will catch interaction bugs early.
- `eval/leak_test.py` consumes its fixtures through `advance_tick` directly
  rather than through `translate_action_intents_for_tick`. That is a
  necessary simplification for fixture authoring (no
  `ActionIntent`-to-`Action` round-trip needed) but it means the leak test
  does not exercise the orchestrator's duplicate-actor rejection path.
  Combined with finding M-2 below, this is a small false-confidence risk.
- No test currently asserts that the audit log is *append-only* across two
  service runs; a future regression that opens the path with `"w"` rather
  than `"a"` would still pass `test_audit_log_records_sanitized_packet`.
  Severity: Low.
- `tests/engine/test_tick.py::test_emergency_requires_actor_in_button_room`
  uses `player-2`, who spawns at `CAFETERIA` per `_state()`. CAFETERIA is the
  emergency button room, so the test relies on the fact that `_state()`
  places `player-2` in `ADMIN`, not the spawn room. Re-reading: yes,
  `_state()` puts `player-2` in `ADMIN`. The test is correct, but the
  fixture/test coupling is implicit. Severity: Low.

## 8. Defects and Risks (ordered by severity)

### M-1 [Medium] Fixture `scripted_game_vent_and_emergency.json` contains a duplicate actor

- **Status:** Fail (test fixture violates the §3.1 "one action per actor per
  tick" contract that the engine assumes).
- **Evidence:** `tests/fixtures/scripted_game_vent_and_emergency.json` lines
  9–11 declare both `{"tick": 2, "type": "vent", "actor": "impostor-1"}` and
  `{"tick": 2, "type": "wait", "actor": "impostor-1"}`. The leak and
  determinism tests call `advance_tick(state, actions_by_tick.get(tick, []))`
  directly, bypassing `translate_action_intents_for_tick`. The fixture
  currently happens to behave correctly only because the `emergency` action
  on the same tick triggers the `MEETING` interrupt (`engine/tick.py:422-423`)
  before the duplicate `wait` runs.
- **Why it matters:** if the fixture is ever extended past this tick, or if
  the meeting-interrupt order changes, the duplicate `wait` would silently
  apply: `_with_actor_last_action` would re-set `impostor-1.last_action` to
  `WaitAction`, masking the prior `VentAction`. The fix is small but the
  current state misrepresents the boundary contract in a place future agents
  will copy-paste from.
- **Recommended action:** replace the trailing `wait` with a different
  actor, or drop it entirely since `emergency` already triggers the meeting.
  Optionally route the eval fixtures through
  `translate_action_intents_for_tick` so the boundary is exercised end-to-end.

### L-1 [Low] `PublicMapView` includes a `vent_rooms` field beyond the contract list

- **Status:** Concern.
- **Evidence:** `observation/public_map.py:23` declares
  `vent_rooms: Mapping[VentId, RoomId]`; the Task 2.1 contract enumerates
  "map id, room ids, room neighbors, vent graph, task locations, spawn room,
  meeting room, and emergency button room" using the word "only".
- **Why it matters:** strict reading would fail the DoD; charitable reading
  treats vent-to-room mapping as topological information agents legitimately
  need (which room a vent surfaces in is the engine-visibility model in
  §3.4). The `extra="forbid"` setting still pins the schema, so it is not a
  drift vector. Worth a one-line note in `tasks/phase-2.md` either way to
  legitimize the field.
- **Recommended action:** update Task 2.1's DoD bullet to include
  `vent_rooms`, or remove the field and have agents re-derive it from
  `vent_graph` + map context. The former is safer; the latter is purer.

### L-2 [Low] Phase-0-adjacent artefacts created outside any task contract

- **Status:** Concern.
- **Evidence:** `api/main.py`, `tests/api/test_main.py`, and
  `docker-compose.yml` exist and are exercised by tests, but no Phase 0 task
  in `tasks/phase-0.md` lists them as in-scope. Their presence is consistent
  with `DESIGN.md` §9 Phase 0 success criteria ("`docker-compose up` boots
  an empty FastAPI") but no explicit task records the work.
- **Why it matters:** the workflow's review discipline is "a task is not
  done until the diff touches only files listed as in scope". These
  artefacts may have been hand-added by the human (allowed per
  AGENT_IMPLEMENTATION.md §5.4 for non-code files, but `api/main.py` is
  code). Future provenance audits will not find them in any task contract.
- **Recommended action:** add a Phase-0 follow-up task contract that
  retroactively scopes `api/main.py`, `tests/api/test_main.py`, and
  `docker-compose.yml`, or move the empty FastAPI scaffolding to early
  Phase 4 where it logically belongs.

### L-3 [Low] `EngineRng` uses `pickle` for state serialization

- **Status:** Concern.
- **Evidence:** `engine/rng.py:31-32` calls `pickle.dumps` /
  `pickle.loads` for snapshot/restore. The docstring acknowledges replays
  are local-only artefacts.
- **Why it matters:** Phase 4 will ship replay artefacts to a spectator UI
  (and possibly Postgres per §1.1). Cross-Python-version replays are not
  guaranteed to round-trip, and `pickle` has well-known security caveats for
  untrusted input. Not a problem now (Python pinned to 3.11; replays are
  local); a problem to anticipate before Phase 4 persistence work begins.
- **Recommended action:** before Phase 4, consider replacing `pickle` with
  an explicit `getstate()`-tuple → JSON encoding, or wrap replays in a
  schema-versioned envelope so cross-version reads can fail loudly.

### L-4 [Low] DESIGN.md §A "sketch" omits the `cooldown` field that §4.2 requires

- **Status:** Concern (documentation drift, not implementation drift).
- **Evidence:** `DESIGN.md:846-854` shows `ObservationPacket` without
  `cooldown`; `DESIGN.md:329-338` includes `cooldown: int | None`. The
  implementation matches §4.2.
- **Why it matters:** §A is labelled "(sketch)" so it is not technically
  authoritative, but downstream agent prompt authors may copy-paste from
  Appendix A. Worth a one-line cross-reference.
- **Recommended action:** add `cooldown: int | None` to the §A snippet
  with a `# impostor only` comment.

### L-5 [Low] Body discoverability flips visibility off for the same observer

- **Status:** Concern.
- **Evidence:** `engine/visibility.py:83-95` filters out bodies whose
  `discovered_by is not None`. Once a player reports a body, that body
  ceases to appear in *any* future packet's `visible_bodies`, including for
  the reporter themselves on the same tick.
- **Why it matters:** in the current MVP this is fine because reporting
  immediately transitions to `MEETING` (no further packets get built for
  that tick), but Phase 2.8's headless orchestrator will iterate over alive
  players and compute observations. If body discovery and observation
  rendering ever interleave inside a single tick, an observer who *just
  reported* would get an empty `visible_bodies`. Belief-state code in Phase
  2.3 may rely on the reporter still seeing the body in the same packet.
- **Recommended action:** clarify in DESIGN.md or in
  `engine/visibility.py`'s docstring whether this is intentional, and add a
  test in Phase 2.8 that pins the desired behaviour.

## 11. Recommended Path Forward

### 11.1 Sequencing through Phase 2

The phase-2 plan already declares the sequencing; this audit confirms it is
the right one for the current state of the repo:

1. **2.2 Agent base + runtime** — sequential. Imports `ActionIntent`,
   `PublicMapView`, `ObservationPacket`. Touches `agents/base.py` and
   `agents/runtime.py` only. Memory/perception/tactical methods are stubs.

3. **2.4 Perception ingestion** — sequential. Adds `agents/perception.py`,
   reads memory write paths from 2.3.
4. **2.5 Pathing** — sequential. Adds `agents/tactical/pathing.py`. After
   this, the spine is in place.
5. **2.6 Crewmate FSM** + **2.7 Impostor FSM** — **parallel** (separate
   files in `agents/tactical/`). Both depend only on 2.5. This is the only
   safe parallel fan-out before the orchestrator integration.
6. **2.8 Headless game orchestrator** — sequential. Wires `seed_initial_state`,
   `HeadlessGame`, `TickScheduler`. Uses the new
   `translate_action_intents_for_tick` from Task 2.1.

- **Replay artefact format vs Python version.** L-3. If replays leave the

### 11.5 Top risks before tactical agents

1. **Memory write paths drift from perception output (Task 2.4)**, leaving
   tactical FSMs reading from an empty memory store. Mitigation: ship 2.3
   and 2.4 with a tight integration test before fanning out 2.6 + 2.7.
2. **A* tie-breaking in Task 2.5.** If the heuristic isn't strict-total,
   determinism dies silently (you'll see flaky win rates instead of
   crashes). The task hint already calls out "tie-break on sorted room id";
   enforce it with a property test that two `find_path` calls with the
   same inputs return the same tuple.
3. **Crewmate / Impostor FSM conflict** — they are declared parallel in
   2.6/2.7. Both consume `MemoryStore` and `PublicMapView`. If 2.5's
   pathing API changes mid-flight, both PRs become rebases. Freeze the 2.5
   API before fanning out.
4. **Headless orchestrator (2.8) inadvertently breaks the leak test.**
   Run `pytest eval/leak_test.py` as part of 2.8's DoD; the contract
   already lists it in the integration-risk callout.

### 11.6 Are the boundary contracts stable enough for downstream agents?

Yes, with one micro-caveat. `ActionIntent` and `PublicMapView` are
Pydantic v2 with `extra="forbid"`, frozen, and engine-free. `ObservationPacket`
is similarly closed. Downstream agent code can pin against these signatures
and rely on the orchestrator translators. The single caveat is L-1: the
extra `vent_rooms` field is currently undocumented in the Task 2.1 contract.
Either way, downstream agent code should consume `vent_rooms` rather than
deriving it from `vent_graph` — better to legitimize than to leave it as a
surprise field.
