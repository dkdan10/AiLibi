## 9. Test Quality and Coverage Gaps

- **The C-3 pin tests are not false positives.** `TestStatementOrderingContract::test_two_round_transcript_is_canonically_ordered` checks SIX distinct assertions covering: round-index monotonicity, the `is_canonically_ordered` predicate, exact statement count, two separate speaker-list pins (round 0 + round 1), and the round-grouping `statements[:3] == tuple(round0)` invariant. The pin would mechanically fail against (a) `asyncio.gather`'d in-round collection, (b) sorted-only speaker order ignoring the reporter, (c) speaker-grouped emission. The companion `test_pin_would_fail_against_speaker_grouped_interleaving` constructs a deliberately-wrong transcript and asserts the predicate rejects it — a genuine "fail against ambiguous ordering" gate.
- **Missed-deadline coverage is per-phase, not aggregate.** Three independent tests at `:523`, `:722`, `:936` each isolate one phase's deadline (setting the other two to `None` for headless mode) and verify the per-phase default constant lands in the transcript. The `:1967 test_meeting_deadline_still_defaults_when_inner_does_not_raise` test is the regression that proves the `_isolate_provider_timeout` wrapper does not over-eagerly re-tag legitimate deadline expiry. This is the genuinely tricky case — Python 3.11+'s `asyncio.TimeoutError == TimeoutError` would have made a naive `except TimeoutError` handler swallow both a deadline expiry and an SDK transport timeout. The fix at [meetings/manager.py:119-136](meetings/manager.py#L119-L136) is a clean separation and the test pins it three ways (report, statement, vote phase).
- **Sibling-cancellation tests use a never-set `asyncio.Event` to prove cancellation, not completion.** `tests/meetings/test_manager.py:2058 test_failing_report_cancels_sibling_report_calls` and `:2082 test_failing_ballot_cancels_sibling_ballot_calls` both assert `client.completed_calls == 0` after the failing voter raises. A naive `asyncio.gather` implementation would let siblings run to completion (or to schema-validation failure) even after the meeting had decided to abort. The `_gather_all_or_cancel` wrapper at [meetings/manager.py:139-167](meetings/manager.py#L139-L167) uses `asyncio.TaskGroup` for true all-or-nothing semantics and the tests verify both the cancellation and the un-wrapping of the `BaseExceptionGroup` to a single exception.
- **Defensive normalization tests cover the actual exploits an LLM could deliver.** `TestInvalidBallotTargetNormalised` at `:1543` plants three failure modes: (a) a hallucinated player id (`"ghost"`) — checks the rationale carries the `INVALID_VOTE_TARGET_MARKER` and the original (bad) target is preserved for audit; (b) voting for self — checks self-vote is treated identically to a hallucinated id; (c) valid target — regression that the normalization path does NOT touch a legitimate ballot.
- **The fake-provider interop test is genuine.** `TestFakeProviderInterop::test_two_runs_with_fake_provider_are_byte_identical` builds two fresh `FakeProvider` instances and two fresh managers, then asserts the resulting `MeetingResult` instances are `==` byte-identical. A subtle nondeterminism in the manager (e.g. participant iteration order, default-vote tick) would surface here.
- **The four prompt templates' tests are exercised indirectly.** There are no per-template unit tests like `tests/agents/strategic/test_crewmate_report.py` that render the `.j2` file with a fixed input and snapshot the output. The prompts are exercised only through `tests/meetings/test_manager.py`'s stub callables (which do not render the `.j2` files at all — they return synthetic `PHASE=REPORT ROLE=CREWMATE ...` strings). This means: the `.j2` syntax could regress (e.g. a malformed `{% endfor %}`) without any CI signal, until Task 3.9 lands the Jinja loader. The DoDs for 3.4–3.7 do not require template-rendering tests; the assumption is that 3.9 will introduce them when it wires the loader. Captured as Concern C-4. Not a defect for 3.4–3.7 individually, but a coverage gap worth flagging for the sub-phase C reviewer.
