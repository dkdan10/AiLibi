## 8. Specific Questions for the Orchestrator + Tournament Layer

1. **Is the determinism boundary clean enough for Phase 3 LLM debugging?** Partially. The tick/action boundary is deterministic: `ReplayEntry` stores tick, actions, and `state_hash` at `orchestrator/replay.py:16-25`, and `record_tick` writes actions plus state hash at `orchestrator/replay.py:43-49`. That is enough to detect divergence, but not enough to isolate a future LLM-caused divergence by itself because it does not record observation packets, rendered memory, prompt text, LLM outputs, or meeting artifacts. DESIGN says LLM determinism requires replaying recorded LLM outputs (`DESIGN.md:805-809`), and Task 3.12 correctly makes that future work explicit (`tasks/phase-3.md:436-448`).

2. **Does `agents/memory/` expose the shape Phase 3.3 needs?** Not cleanly enough. Task 3.3 names `agents/memory/store.py::render_for_prompt` and expects role, task totals, salience-sorted observations, beliefs, and contradictions (`tasks/phase-3.md:96-129`). Today `agents/memory/store.py` does not exist; `agents/memory/episodic.py:33-58` exposes only an append-only episodic log, while `BeliefState` is a separate object at `agents/memory/beliefs.py:91-141`. Phase 3.3 can create the missing aggregate, but the current shape gap should be closed before prompt rendering starts.

3. **Does the orchestrator expose a clean meeting interpose point?** Mostly yes. The pause point is a single localized branch immediately after `advance_tick`: `orchestrator/game.py:141-151` records the tick and returns `MEETING_PHASE_REACHED` when `state.phase == "MEETING"`. It is not factored into a named `_handle_meeting_phase` method, so Phase 3.12 will edit the loop body, but the replacement is localized and should not require surgery across packet dispatch or action collection.

4. **Is the leak test strong enough to catch Phase-3 LLM prompt leaks?** Not yet. It is strong for `ObservationPacket` values: field and value scanners exist at `eval/leak_test.py:158-199`, and they passed scripted, seed-42, and 100-game audit logs. It does not scan rendered memory or prompt text because those surfaces do not exist yet; Phase 3.3/3.9 need to reuse or generalize the scanner against `render_for_prompt` outputs and strategic prompt inputs.

5. **Are there hardening tasks Phase 3 would compound?** Yes: fix the default-game/tournament outcome failure first; clean the old-id grep guard so the role-neutral rename invariant has a usable mechanical check; define the memory aggregate for `render_for_prompt`; and extend leak scanning to rendered memory/prompt strings before any LLM prompt is consumed.

## 9. Test Quality and Coverage Gaps

- No CI test currently enforces the Phase 2 merge criterion on a real default-agent tournament. `tests/eval/test_balance_eval.py` verifies bucket accounting, replay files, and small leak scans, but the real 100-game CLI run fails the balance criterion.
- Task 2.8.5's six-seed decisive-outcome gate is not pinned by a failing test. The required CLI sweep catches the problem, but the green suite does not.
- The remaining-task probe shows a likely behavioral gap: after one kill, the surviving crewmates can complete their own tasks while the dead crewmate's task remains incomplete forever.
