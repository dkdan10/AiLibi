# MVP-Close Audit — 2026-05-30 00:59

## 1. Verdict

**MINOR_REPAIRS_NEEDED**

The AiLibi MVP substrate is sound at every load-bearing seam that gates correctness. The information-leakage firewall holds end-to-end: the import-linter contract forbids `agents → engine`, no such import exists, the `ObservationPacket` schema confines `role` to `self_state`, and the prompt-generation path (D-3, verified-true) embeds only the speaking agent's own role — no cross-player role, kill attribution, or raw engine state reaches the LLM. Determinism (state-hash + recorded-action replay) is tested, the 50 committed sample replays all reconstruct byte-for-byte, the schema mirror (Python DTOs ↔ TS interfaces) is 1:1 with all 81 prompts in sync, and the win-condition ordering, voting threshold, and budget caps all match their DESIGN.md contracts. No surviving finding is a correctness defect in shipped code or an active data leak. That is why this is not SIGNIFICANT_REPAIRS_NEEDED.

It is also not SUBSTRATE_CLEAN, for two reasons. First, DESIGN.md has drifted materially from the implemented architecture: it presents PostgreSQL/JSONB persistence, a WebSocket real-time push layer, a `render_replay.py` debug tool, a `POST /games` route, and a five-rule belief model as current architecture, when the implementation is JSONL-on-disk persistence, a static read-only replay API, a live React spectator UI, CLI-driven game creation, and a two-rule (1 and 4) belief model that is in fact dormant in headless games because `AgentRuntime._perceive` never passes a `BeliefState` (A-1, A-2, A-3, A-4, A-7). These are documentation-vs-code coherence gaps, not code defects, but the design document is the project's source of truth and a reader cannot currently trust it as a description of HEAD. Second, the agent-intelligence substrate has a cluster of "exists-but-dead" gaps: the contradiction detector is never called in the live meeting loop (J-1), the impostor policy never vents or sabotages so belief Rule 4 and the sabotage win path are agent-unexercised (J-5), and the win-condition has no impostor-elimination case so games run on as zombies after the last impostor is ejected (J-8, also I-3). These are deferred-feature gaps consistent with project memory, but several are mislabeled in DESIGN.md as implemented.

The actionable repair surface is dominated by documentation reconciliation (Class A, Class F), two parallel-surface contract harmonizations on the new Phase 5 `/eval/tournament-report` endpoint (B/D cluster), three test-invariant pins for known-deferred behavior (Class I), and a set of frontend performance/accessibility items that are explicitly scoped as inputs to the Phase 6 redesign brief (Class K). The single highest-urgency operational item is the docker-compose `0.0.0.0` bind of the unauthenticated GM-view API (C-1) — harmless while local-only but a full ground-truth exposure the moment anyone runs `docker compose up` on a shared network. None of these block the MVP-complete claim; all are repairs that keep the design document honest and harden the surface before Phase 6.

## 6. Forward-looking observations

- The agent-intelligence substrate's three load-bearing deception/detection signals — contradiction flags, witnessed-vent suspicion (Rule 4), and contradiction-derived suspicion (Rule 2) — are all dead in live play today (J-1, J-4, J-5). Phase 6's "smarter agents" goal has a hard prerequisite chain: wire the detector (J-1) → roster-aware subject matching (J-9) → belief Rule 2 (J-4) → new detector kinds (J-2). None of this is reachable until the detector is called in the meeting loop. The production `AgentRuntime` also does not pass a `BeliefState` into perception (A-4), so even the two implemented rules are dormant — this must be fixed for any belief-driven behavior to manifest in headless games.
- The win-condition incentive defect (J-8) distorts the eval/balance numbers that gate agent-intelligence work: games the crew has effectively won record as non-decisive or task-completion wins, so the "36% impostor win rate" the README and balance dashboard report is computed over a population that includes zombie games. Closing J-8 (with fixture regeneration) should precede any balance-tuning that depends on those aggregates.
- The entire scale path DESIGN.md §7 names (workers + Redis pubsub fanning out live tick/meeting events) presupposes a WebSocket live-broadcast layer that does not exist (A-2, H-1). The first real pre-scale task is not "port to Redis" but "design and build the single-process live-broadcast layer (connection registry, tick/meeting fan-out)" — the substrate for Phase 6 human-player seats. Until that exists, the persistence (Postgres), process-orchestration (Redis pubsub), and async-worker (H-4) scale concerns have no code to migrate.
- The frontend is built as a fixed-desktop, front-load-everything spectator (K-1, K-3, K-5) with a single 800×600 canvas, no windowing, and rich backend DTO fields (names, alive/dead, actions, task progress, failed_calls, winner_reason) produced but never surfaced. The Phase 6 UI redesign should treat the existing `getTick`/`getMeeting` endpoints as the windowing primitives, decide a payload-windowing strategy before scaling game length, and surface the data already on the wire before adding new data.
- The leak-test firewall, the single most important correctness guarantee, currently pins only the curated `api.schemas` surface and walks three fixed fixtures (B-2/D-2, I-2). As Phase 6 adds surfaces (a live WebSocket payload, human-player views), the firewall must be extended to cover every served schema and run as a many-seeds property sweep, or new surfaces will ship outside its coverage exactly as the Phase 5 `/eval/tournament-report` endpoint did.
