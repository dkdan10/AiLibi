1. **Task 2.4 scope drift** — the 2.4 PR modified `agents/runtime.py` to wire

   — the agents now exist but no test runs them through `advance_tick` and

   deferred-by-design to Task 2.8 but worth pinning before that task starts).
3. **`CrewmatePolicy._move_toward` and `CrewmatePolicy._flee_and_report` do
   not catch `ValueError` from `find_path`** — disconnected/unknown rooms in
   working memory would crash the agent rather than degrade to wait. The
   canonical map is fully connected so this is currently latent (Low).
4. **The crewmate `KILL_WITNESSED` interrupt is narrower than the engine's
   visibility model** — it only fires when the kill action is reported in the
   agent's own room, even though `engine/visibility.py::same_room_and_adjacent`
   may surface the action in an adjacent room. This is a tactical choice, not
   a contract violation, but worth documenting (Low).
5. **Perception's `_AUDIBLE_EVENT_TYPES` is a closed allow-list** — any new
   `AudibleEvent.kind` added in `observation/packet.py` will raise from
   perception until perception is updated. Tight coupling to a small enum;
   acceptable but flagged so engine-side authors know to update perception
   alongside (Low).

No Critical or High findings. The boundary contracts that Task 2.1 stabilised
remain intact. The four Concern/Low findings do not block Task 2.8.

## 9. Specific Questions for the New Agent Layer

1. **Do new agent classes import only from `agents/`, the boundary contracts,
   and stdlib?** Yes — see the per-module import table above. No `engine`,
   no `llm`, no `orchestrator`.
2. **Are there scenario tests driving multiple agents through full
   episodes?** No. Deferred to 2.8 by scope. Concern noted in §8.
3. **Adversarial leak tests for new agent paths?** No new leak tests landed
   in 2.2–2.7. Existing `eval/leak_test.py` covers the
   engine→ObservationPacket boundary (which is what perception consumes), so
   if the firewall holds at the packet, perception cannot widen it. New
   agent-side leak tests (e.g., asserting that a crewmate's `MemoryStore`
   never accumulates `cooldown_status` events) would still be valuable
   pre-2.8.
4. **Failure-mode coverage (malformed intents, illegal moves, duplicate
   submissions, dead-actor submissions, role-illegal intents)?**
   - Malformed intents: covered at the boundary
     (`tests/orchestrator/test_boundary.py`); the new agent code never
     constructs intents from arbitrary input — every intent is built from
     fixed payload dicts via `model_validate`, so a bad intent shape
     would surface at construction time.
   - Illegal moves (e.g., `MoveIntent` to a non-neighbor): not
     prevented in the agent — the policy always returns a single A* step,
     which is by definition a neighbor. If `find_path` returned a
     malformed path, the engine would reject it via
     `ActionRejectedError`. Defense-in-depth via the engine.
   - Duplicate submissions / dead-actor submissions: enforced at the
     orchestrator boundary (Task 2.1, unchanged). Not exercised
     end-to-end with agent code yet.
   - Role-illegal intents (e.g., a crewmate emitting `KillIntent`): not
     prevented in the policy — the engine rejects (rules.py). The current
     policy implementations cannot construct such intents because each
     branch is hard-coded to a specific intent class.
5. **Are any new helpers in `agents/` doing engine work?** No.
   `pathing.py` consumes `PublicMapView.room_neighbors` (the public
   topology) rather than computing reachability from raw map data. The
   crewmate's `_first_visible_body` and `_kill_witnessed` filter
   episodic events; they don't reach into engine state.
6. **Duck-typed engine access?** None. Every cross-package import is an
   explicit `from observation.* import …` or `from agents.* import …`.
   No `getattr` on engine types, no `importlib.import_module("engine…")`.
7. **Deterministic hashes stable across two runs of the new scenario tests?**
   Ran `eval/determinism_test.py` twice; identical pass count and timing.
   The new agent tests use synthesised `MemoryStore`s, so determinism is
   verified at the policy level by repeated `decide` calls returning equal
   intents (`TestCrewmateDeterminism::test_repeated_decide_calls_return_equal_intents`,
   `TestImpostorDeterminism::test_repeated_decide_calls_return_equal_intents`).
   Cross-run state-hash comparisons for agent-driven games await Task 2.8.

## 10. Test Quality and Coverage Gaps

Strengths:

- Each new module has a thoughtful unit test file averaging ~300 lines, with
  organisation into nested classes by responsibility (idle/normal,
  interrupts, validation, determinism). Coverage of error paths is
  consistent: every `raise ValueError` in the policies has a matching
  test (`TestImpostorInputValidation` covers the three input-validation
  errors in `impostor_policy.decide`).
- Determinism is tested at two levels: repeat-call equality
  (`policy.decide` 5×) and order-independence (forward vs reversed
  neighbour tuples).
- Tie-breaker semantics are pinned (`pathing` diamond-graph test,
  impostor's `test_stalk_picks_alphabetically_first_id_when_scores_tie`).
- The crewmate's interrupt priority is pinned
  (`test_body_visible_takes_priority_over_kill_witnessed`).

Gaps:

- **No agent-driven multi-tick replay test.** As above. Owned by 2.8.
- **No fuzz / property test for `ActionIntent` round-trip** (intent →
  engine `Action` → JSON → engine `Action`). Listed as a recommended
  pre-Phase-3 hardening in the prior audit; still unaddressed.
- **No leak test specific to per-agent memory contents.** A regression
  that leaked, say, killer identity into `_visible_player_payload`
  would currently pass the engine→packet leak test but corrupt agent
  memory. A small assertion that crewmate `MemoryStore`s contain no
  `cooldown_status` events would catch one common drift.
- **No test asserting `_AUDIBLE_EVENT_TYPES` matches the
  `AudibleEvent.kind` enum.** If a kind is added in
  `observation/packet.py`, perception will start raising at runtime
  instead of failing CI.
- **Crewmate's `_move_toward` and `_flee_and_report` do not catch
  `ValueError` from `find_path`.** No test covers a disconnected map. The
  current canonical map is fully connected so this is latent, but a
  regression test pinning either "fail loudly" or "fall back to wait"
  would prevent silent crashes when 2.8 starts driving real games.

### L-3 [Low] Crewmate `KILL_WITNESSED` interrupt narrower than engine visibility

- **Status:** Concern.
- **Evidence:** `agents/tactical/crewmate_policy.py:158-172` only fires
  the interrupt when `event.payload.get("room") == own_room`. The
  engine's visibility model
  (`engine/visibility.py::same_room_and_adjacent`) emits visible-player
  rows for adjacent rooms too, so a crewmate watching a kill from the
  next room over does not interrupt their task.
- **Why it matters:** The DESIGN.md §4.4 hint says
  `KILL_WITNESSED -> FLEE_AND_REPORT`. The narrower trigger is a

  to deterministically), but it is not documented as such anywhere
  outside the policy docstring. Future authors may think the FSM is
  buggy.
- **Recommended action:** either widen the trigger to "any kill in the
  visible window" or add a one-line note in `tasks/phase-2.md` Task 2.6
  recording the deliberate narrowing.

### L-4 [Low] Perception's `_AUDIBLE_EVENT_TYPES` is a closed allow-list

- **Status:** Concern.
- **Evidence:** `agents/perception.py:44-47` hard-codes the mapping for

- **Why it matters:** the engine and perception now have an implicit

- **Recommended action:** add a unit test that imports
  `observation.packet.AudibleEvent` and asserts
  `set(_AUDIBLE_EVENT_TYPES) == {kind for kind in AudibleEvent's
  Literal type}`. Or move the mapping into `observation/packet.py` next
  to the type definition.

### L-5 [Low] No regression test pins body-visibility-after-discovery yet
